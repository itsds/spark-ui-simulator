# Scenario backlog

Priority order. Each scenario = workload + **injected cause**. The symptoms
must come out of the simulation (see ARCHITECTURE.md, realism rules).
"Evidence" lists where a good engineer finds the proof in the real Spark UI;
`solution.md` must quote the exact numbers, and a test checks them.

Workload parameters can describe the job's code at the time of a run: `clickstream_enrichment` takes
`broadcast_hint` (the `F.broadcast()` around the page catalog, in the script since 2026-09-24; Scenario 05 runs
without it), `geo_udf` (release 2.4's `geoip_city` UDF and its `--jars` / `--files`; Scenario 03) and
`geo_reader` (`per_task`, or `per_executor` for the fixed UDF), and `events_read` (`partition_path`: the day's
directory with basePath; `event_date`: DATA-4398's root read filtered on a shadowing `dt`, Scenario 06;
`event_date_pruned`: its fix), and `customers_current` (filter the customer history's `is_current` before the
join: Scenario 07's fix). A code change like this can be an incident's cause on its own (no fault needed).
Input tables can be partitioned (`InputDataset.partitions`, `arrival_lag`; ADR-046): the planner prunes them with
the scan's PartitionFilters as Spark does. Fault mechanisms available in `scenario.yaml` (Phase 6, ADR-029): `key_skew` (hot keys, Zipf), `duplicate_keys`
(a dimension that keeps several rows per key, e.g. an SCD2 history: rows, files, appended columns; a join's output
follows, ADR-049), `config`,
`slow_node` (CPU/disk/NIC; the CPU factor also stretches deserialization, codegen, JVM start-up, ADR-037),
`memory_pressure` (native memory per task), `executor_killed` (SIGKILL, exit 137), `yarn_preemption` (another
queue reclaims containers: exit -102, no replacements until `until`). The engine also models
speculative execution (`spark.speculation`, ADR-036) and `spark.yarn.exclude.nodes`.
The planner also follows `spark.sql.adaptive.coalescePartitions.initialPartitionNum` (Scenario 02's durable
fix). Since Scenario 03 the engine also aborts a job at `spark.task.maxFailures`, fails the
application and runs YARN's second attempt (ADR-041). Since Scenario 12 it models
lost shuffle files without the shuffle service (Resubmitted, FetchFailed, stage attempts; ADR-044) and YARN
preemption (`yarn_preemption`: another queue reclaims its share, the app's youngest containers go first). Still to
build for the backlog: task exceptions (`ExceptionFailure`), AQE's skew-join split (a "fixed run" for 01), GC
pressure (08), Python UDF nodes (10), queue capacity (14).

Later: Structured Streaming (ADR-005), dynamic-allocation thrash, broadcast timeout / driver OOM, "AQE working as intended" (to recognize success).

Also later: **an attempt 2 that behaves differently** (succeeds, or fails another way): the engine runs
YARN's second attempt since Scenario 03 (ADR-041); a flaky cause (a marginal memory footprint, a bad node)
could make attempt 1 fail and attempt 2 succeed, which the History Server shows as two attempts of one
application.
